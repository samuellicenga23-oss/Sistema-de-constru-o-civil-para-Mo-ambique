1. DADOS GERAIS DO PRODUTO
================================================================================

1.1 Identidade
--------------
Nome comercial:          SIGO
Nome completo:           Sistema Integrado de Gestão de Obras
Tipo de produto:         SaaS B2B multi-empresa (multi-tenant)
Domínio:                 Construção civil — orçamento, planeamento, compras,
                         execução de obra, medição e controlo financeiro
Slogan / mensagem:       "Controle a obra como ela realmente acontece."
Posicionamento:          Uma plataforma que liga estimativa → orçamento →
                         cronograma → compras → diário de obra → autos →
                         financeiro, sem folhas de cálculo paralelas.

1.2 Problema que resolve
------------------------
- Excel e ficheiros dispersos por obra, sem versão única
- Preços de materiais desactualizados no orçamento
- Diário e Autos desligados do cronograma
- Compras decididas sem cruzar stock e necessidades do plano
- Falta de rastreabilidade entre planta, quantidade, composição e preço

1.3 Utilizadores-alvo (personas)
--------------------------------
- Construtora / empreiteiro: margem, produção, compras, autos
- Fiscalização: evidência, medição, aprovação
- Dono da obra: prazo, compromisso financeiro, visão consolidada
- Orçamentista: mapas, composições, catálogo, zonas de preço
- Encarregado / campo: diário, avanço físico (via perfis existentes)

1.4 Contexto normativo / operacional (Moçambique)
-------------------------------------------------
O produto alinha-se conceptualmente com fluxos de empreitadas usados no país
(orçamento e cronograma físico-financeiro, auto emitido pelo empreiteiro,
certificação pela fiscalização, suporte ao pagamento), e com a necessidade de
justificação escrita em contratação pública (ex.: Decreto n.º 79/2022), sem
substituir assessoria jurídica ou certificação contabilística oficial.

1.5 Estado de maturidade (para especificação de lançamento)
-----------------------------------------------------------
- Uso actual recomendado: pilotos controlados com validação humana de
  medições automáticas, preços e autos
- Não apresentar o SIGO como fonte final de verdade para quantidades
  extraídas automaticamente, aprovação contratual definitiva ou
  contabilidade certificada
- Princípios de produto: isolamento multiempresa; documento aprovado
  imutável (alteração = revisão); rastreio de origem de valores;
  medição automática = sugestão confirmável por técnico

2. ARQUITECTURA TÉCNICA (VISÃO GERAL)
================================================================================

2.1 Monorepo (npm workspaces)
----------------------------
apps/web            Frontend React + TypeScript + Tailwind (Vite)
apps/api            Backend Node.js + TypeScript + Fastify + Drizzle ORM
apps/plant-service  Microserviço Python (FastAPI) — leitura de plantas PDF
packages/shared     Tipos, enums, schemas Zod e catálogo de permissões

2.2 Infraestrutura típica de produção
-------------------------------------
- Hospedagem: VPS (ex.: Hostinger CloudPanel)
- URL produção: https://sud30s.org
- API: processo PM2 (ex.: sigo-api)
- Base de dados: PostgreSQL (acesso tipicamente só localhost; túnel SSH
  para administração remota)
- PDF: gerado na API via Puppeteer (não é serviço separado)
- Plantas: plant-service em processo/serviço próprio (porta tip. 8001)

2.3 Portas locais de desenvolvimento
------------------------------------
Frontend (Vite):     http://127.0.0.1:5273
API (Fastify):       http://127.0.0.1:4100  (configurável; default env ~4000/4100)
Plant-service:       http://127.0.0.1:8001

2.4 Autenticação
----------------
- Sessão por cookie HTTP (sid), TTL tipicamente 7 dias
- Login email + palavra-passe
- Login Google OAuth (opcional; só associa a conta já criada pelo admin)
- Conta inactiva: rejeição explícita (mensagem clara, não "credenciais inválidas")
- Subscrição suspensa da empresa: bloqueio de login
- Alteração forçada de palavra-passe no primeiro acesso (mustChangePassword)

3. MODELO MULTI-EMPRESA E MÓDULOS
================================================================================

3.1 Tenant
----------
Cada cliente opera numa "empresa" (company). Dados operacionais são isolados
por company_id. Super Admin da plataforma gere empresas e subscrições sem
entrar nos dados operacionais de obra como utilizador normal.

3.2 Módulos activáveis por empresa (enabledModules)
---------------------------------------------------
dashboard
measurements          (medições / plantas)
budgets               (orçamentos / documentos)
catalog               (catálogo e composições)
suppliers             (fornecedores)
purchasing            (compras e stock)
schedule              (cronograma)
site_diary            (diário de obra)
financial             (financeiro / autos / contratos)
quick_calculations    (cálculos rápidos)

Nota: o super_admin pode activar/desactivar módulos por empresa.
O frontend e o backend filtram rotas/APIs conforme os módulos activos.

3.3 Moedas e unidades
---------------------
Moedas: MZN, USD
Unidades típicas: m, m2, m3, ml, kg, un, vg, h
Preços podem variar por fornecedor e por zona geográfica

4.2 Modelo de permissões (RBAC com override)
--------------------------------------------
- Catálogo de permissões com IDs estáveis (nunca só labels)
- Template padrão por função (role → permissionIds[])
- Cópia do template ao criar utilizador
- Ajuste fino por utilizador (lista própria)
- Acção "Restaurar padrão da função"
- Templates personalizáveis por empresa (role_permissions)
- Alterar template afecta novos users; overrides mantêm-se até restaurar
- Conta inactiva não autentica; sessões são revogadas ao desactivar

================================================================================
6. FLUXOS PRINCIPAIS DE NEGÓCIO (PARA CASOS DE USO)
================================================================================

Fluxo A — Da planta ao orçamento
  1. Criar projecto (tipo medição; modo plantas/manual)
  2. Carregar PDF(s) — processamento assíncrono
  3. Confirmar compartimentos, vãos, lajes (e armaduras se estrutura)
  4. Gerar / completar medições (assistente ou fill-from-plant)
  5. Enviar para orçamento
  6. Aplicar composições, zonas e preços; resolver itens sem preço
  7. Submeter e aprovar orçamento

Fluxo B — Execução e certificação
  1. Orçamento aprovado
  2. Gerar / editar cronograma (WBS + Gantt)
  3. Registar diário e avanço (e consumos de stock)
  4. Abrir Auto de medição do período
  5. Submeter à fiscalização → aprovar
  6. Reflectir no financeiro / emitir factura a partir do auto

Fluxo C — Compras
  1. Necessidades a partir do MQ/composições e stock
  2. Comparar cotações (zona + SIGO Preços como referência)
  3. Criar ordem de compra com fornecedor comercial
  4. Aprovar / receber / movimentos de stock

Fluxo D — Administração de acessos
  1. Admin cria utilizador com função
  2. Sistema copia permissões padrão da função
  3. Admin ajusta permissões do user (opcional)
  4. Admin pode restaurar padrão ou editar template da função

Fluxo E — Controlo de qualidade documental
  1. Só rascunho é editável
  2. Submeter exige readiness (quantidades/unidades/preços)
  3. Aprovado bloqueia edição; nova revisão para alterar
  4. Banner “Próximo passo” orienta a obra


================================================================================
7. ESTADOS E REGRAS DE DOCUMENTOS
================================================================================

Estados de documento (mapa / orçamento):
  rascunho → submetido → aprovado

Regras:
  - Em submetido/aprovado: edição operacional bloqueada no FE e na API
  - Aprovado: alterações via nova revisão
  - Auto de medição: requer orçamento aprovado elegível
  - Stock: não permitir saída acima do saldo
  - Auditoria: eventos imutáveis (audit_events) para mudanças de estado
    relevantes (mapas, autos, OC, financeiro, stock manual, utilizadores)
